# Author Blender assets for arpg

Treat Blender as a deterministic asset compiler. Versioned Python and authored
source assets feed the engine's import contract; a live Blender session is
optional and its state is never the only copy of accepted work.

## Establish the asset contract

Identify whether the target is a static mesh, player character, ordinary horde
character, or world asset. Read the owning contract before editing:

- For static meshes and skinned characters, read
  [character asset authoring](../../../docs/character-assets-authoring.md).
- Read the target directory's README and generator, if present.
- Read the relevant importer and its tests in `crates/assets` when the request
  touches an accepted GLB feature or boundary. The importer owns the supported
  subset; do not infer it from Blender's full export surface.
- Read presentation role resolution in `crates/app/src/presentation.rs` when
  changing clip names, player roles, horde roles, or default asset selection.

State the asset's intended scale, facing, mesh/material/texture limits, rig and
clip requirements, and visual acceptance target before authoring. Preserve the
shared convention: metres, Blender Z-up, and Blender `-Y` facing unless the
owning contract explicitly changes.

## Establish motion quality

For new characters or visible model/motion work, use
[character-workflow](../character-workflow/SKILL.md) for references, visual
development and review. Reuse already established targets and accepted passes.
This skill owns the technical compilation and export path. Structural validity
and additional joints do not certify visual quality.

## Keep durable source

Create or edit a narrowly scoped `bpy` generator beside the asset. Follow the
existing generators instead of building a second framework. The script should:

1. Start from known empty state rather than depend on the open file.
2. Create or import named geometry, transforms, materials, packed textures,
   rigs, weights and actions from explicit versioned inputs.
3. Apply transforms at the boundary required by the importer.
4. Save the editable `.blend` and export the runtime `.glb`.
5. Use explicit exporter options and assert required Blender operators return
   `{'FINISHED'}`.

Do not hand-edit generated `.blend` or `.glb` files. Interactive sculpting,
weight painting and posing can be retained in a distinct versioned source
`.blend` that the generator imports. Capture accepted changes in those source
inputs or Python before regenerating both outputs. Do not add MCP merely to run
work that the Blender CLI and `bpy` already support.

Prefer Blender's data API where practical. `bpy.ops` is context-sensitive, so
set selection, active object, mode, and frame deliberately before an operator
and verify its result.

## Build in isolation

Run from the repository root. First regenerate into a temporary directory when
the generator accepts an output argument:

```sh
out=$(mktemp -d /tmp/arpg-blender.XXXXXX)
blender --background --factory-startup --python-exit-code 1 \
  --python assets/characters/basic-player/generate.py -- "$out"
```

`--factory-startup` prevents user preferences from becoming hidden inputs, and
`--python-exit-code 1` makes Python failures fail the command. Record
`blender --version` in the handoff when generated bytes change. Use the command
documented beside other assets, adapting only its output path.

For a new or materially changed generator, perform two clean temporary builds
and compare the GLBs. Investigate nondeterminism rather than normalizing it
away. Compare a clean result with the checked-in artifact before replacing it;
an unchanged asset should be byte-identical. Copy generated artifacts into the
asset directory only after the isolated build passes.

## Verify structure and appearance

Validation has three distinct jobs; none substitutes for another:

1. Run the focused `crates/assets` contract tests for the asset, then
   `cargo test --workspace`. Tests must exercise the properties the engine
   relies on: dimensions/orientation, texture shape, joints and weights, bind
   pose, clip catalog, and meaningful animation samples as applicable.
2. For a visible geometry, material, rig, or animation change, produce and
   inspect deterministic diagnostic renders. Use front, side, back, and
   three-quarter views for geometry. For player attacks also inspect the
   authored phase edges—currently frames 1, 13, 19, and 31. Keep diagnostic
   renders temporary unless the user asks to retain them.
3. Use the [playtest skill](../playtest/SKILL.md) to load characters through
   `character show` or `horde show`. For static world assets, regenerate the
   corresponding [ground or prop asset](../../../assets/world/README.md), restart
   the app, and load a scene containing the relevant placements. Capture the
   game's own screenshot and inspect the real camera, shading, scale, and
   animation mapping. This is the final visual truth.

If an installed Khronos glTF Validator is available, run it as a complementary
format check. Do not install new tools without the task requiring that scope.
The Rust importer remains the authoritative check for arpg's narrower subset.

## Finish with evidence

Report the generator and artifacts changed, Blender version used, regeneration
result, tests run, and visual views inspected. Separate automated contract
evidence from subjective appearance judgments. An asset is unfinished if only
the source or only the generated binary was inspected.
